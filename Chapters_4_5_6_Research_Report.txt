4.1 Introduction

This chapter presents how the Enzama Looks online salon booking system
was built. It describes the implementation environment, the modules
that were coded, how those modules were integrated, the database
design, selected source-code excerpts that illustrate the core
business logic, the procedure for installing and running the system,
and the practical problems that arose during development.

The chapter answers the question: what was actually constructed to
address the problem of informal, error-prone appointment booking at
Enzama Looks in Entebbe? The problem, as framed in Chapter 1, is that
clients typically book by walk-in, telephone or WhatsApp. That
practice produces double-booked chairs, missed reminders, weak
records of services and revenue, and no single view of which
professional is free at a given time. The system implemented here
gives guests a public booking path that does not require an account,
gives administrators tools to manage the catalogue and the diary, and
gives professionals a restricted portal for their own appointments.

Development and demonstration were carried out on a personal computer

4.2.3 Programming languages, frameworks and libraries

TypeScript was used throughout so that roles, booking statuses and
service categories are checked at compile time rather than discovered
as runtime bugs. Next.js App Router pages are React Server Components
by default. Mutations (creating a booking, changing a status, saving
a professional) are Next.js Server Actions in app/actions/. Client
components are used only where the browser must hold stepwise state,
principally the four-step booking wizard and the dashboard calendar.

Prisma 7 does not embed the database URL in schema.prisma. Connection
settings live in prisma.config.ts and in environment variables. The
MariaDB driver adapter is constructed in lib/prisma.ts so that the
same client can be reused across requests without exhausting the
connection pool.

Auth.js issues a JWT session. Passwords are never stored in plain
text; bcryptjs hashes them with a cost factor of 10. Route protection
is applied twice: in proxy.ts (edge/request level) and again in
server layouts through requireAdmin() and requireProfessional().


4.2.4 Database platform

MySQL was selected because it is widely taught, free, and adequate
for a single-salon workload. String primary keys use cuid() values.
Enums constrain Role (ADMIN, PROFESSIONAL), BookingStatus (PENDING,
CONFIRMED, REJECTED, CANCELLED, COMPLETED) and ServiceCategory (HAIR,
COLOR, BRAIDS, BARBER, NAILS, MAKEUP, LASHES_BROWS, SKIN_SPA, WAXING).
Money is stored as DECIMAL(12,0) Ugandan shillings. Indexes were
placed on role, isActive, category, professionalId+startAt, status
and startAt, matching the queries used by the dashboards and the
slot engine.

Two Prisma migrations were applied:

  20260815120000_init
      Creates User, Professional, Service, ProfessionalService,
      WorkingHour, Booking, BookingService and SalonSettings.

  20260820120000_booking_reminder_sent
      Adds Booking.reminderSentAt so a same-day reminder is sent
      at most once.

4.3 System Architecture

The system follows a three-tier web architecture.

  Presentation tier
      Marketing pages (/), the booking wizard (/book), the login
      form (/login), the admin dashboard (/admin/*) and the staff
      dashboard (/staff/*). Shared UI primitives live in
      components/ui/.

  Application tier
      Next.js server: Server Components fetch data; Server Actions
      mutate data; lib/availability.ts computes free slots;
      lib/mail/* sends mail; lib/auth.ts authenticates users.

  Data tier
      MySQL database accessed only through Prisma.

A simplified request path for a guest booking is:

  Browser  ->  BookingWizard (client)
           ->  createGuestBooking (server action)
           ->  Zod validation
           ->  professionalsForServices + getSlotsForDate
           ->  Prisma INSERT Booking + BookingService rows
           ->  notifyBookingCreated (email, non-blocking)
           ->  confirmation card in the browser

A simplified path for a staff decision is:

  Professional signs in  ->  JWT with role PROFESSIONAL
                         ->  /staff/bookings
                         ->  staffUpdateBookingStatus
                         ->  Prisma UPDATE + status email

4.4 Database Design

4.4.1 Entity-Relationship Diagram

The schema is defined in prisma/schema.prisma. Guests are not Users.
A User is only a salon employee (administrator or professional).
Client identity is stored on the Booking row itself (name, phone,
email, location). That design matches the requirement that the public
must not be forced to register.

A Professional is a 1:1 extension of a User. Services are offered by
many professionals through the ProfessionalService join table.
WorkingHour stores seven rows per professional (Sunday = 0 through
Saturday = 6). BookingService snapshots the price and duration at
the moment of booking so later catalogue edits do not rewrite
history.

Figure 4.4: Entity-Relationship Diagram (conceptual)

  User 1 ----------- 0..1 Professional
   |                      | 1
   | assignedBy           |---- WorkingHour (1:N, unique per weekday)
   |                      |
   |                      |---- ProfessionalService (M:N) ---- Service
   |                      |
   |                      | 1
   |                      +---- Booking (1:N)
   |                                |
   |                                +---- BookingService (M:N) ---- Service
   |
   SalonSettings (single row, id = 1)

  Cardinality notes:
  - User.role is ADMIN or PROFESSIONAL.
  - Only PROFESSIONAL users have a Professional profile.
  - Booking.professionalId is required (a chair must be assigned).
  - Booking.assignedById is optional (set when an admin reschedules).
  - Booking.reminderSentAt is null until the same-day reminder goes out.

4.5.2 Guest booking module

Route: /book
Client: components/booking/booking-wizard.tsx
Server: app/actions/booking.ts

The wizard has four steps: Services, Professional, Time, Your
details.

Step 1 — the guest searches or filters by category and ticks one or
more services. Duration and total price update live.

Step 2 — only professionals who offer every selected service remain
eligible. The guest may pick one stylist or leave the choice as
"any", in which case slots from all eligible stylists are listed.

Step 3 — the guest picks a Kampala calendar date. getSlotsForDate
reads that professional's WorkingHour row, subtracts PENDING and
CONFIRMED bookings that overlap the day, and returns start times at
the salon slot interval (default 30 minutes). getSuggestedSlots
looks up to ten days ahead and offers three soonest free times so
the guest is not stuck if today is full.

Step 4 — name, phone, email and location are required. On submit,
createGuestBooking validates with Zod, rejects past times, confirms
the professional still offers the mix, re-computes slots so a race
cannot double-book the same chair, then inserts the booking as
PENDING with price and duration snapshots. An email of kind
"received" is fired without blocking the HTTP response.

4.5.3 Authentication and access control

Route: /login
Actions: app/actions/auth.ts
Library: lib/auth.ts, lib/auth.config.ts, proxy.ts

Guests never authenticate. Staff use email and password. loginAction
looks up the user, rejects inactive accounts, compares the bcrypt
hash, then calls Auth.js signIn. Administrators are redirected to
/admin; professionals to /staff.

proxy.ts intercepts /admin, /staff and /login. Unauthenticated
visitors are sent to login with a callback URL. A professional who
opens /admin is bounced to /staff, and the reverse. Layouts call
requireAdmin() or requireProfessional() so a forged request that
somehow passed the proxy still cannot run privileged Server Actions.

JWT claims carry id, role and professionalId. That last claim lets
staffUpdateBookingStatus refuse updates to another stylist's diary.

4.5.6 Availability and scheduling engine

Library: lib/availability.ts

Times are constructed as Africa/Kampala instants (+03:00), not as
naive UTC clock times. buildSlots walks from the professional's
startTime to endTime in intervalMin steps and keeps a candidate
only if the full duration of the selected services fits before
endTime and does not overlap any busy range. overlaps uses the
standard half-open test: a.start < b.end AND a.end > b.start.

Monday is seeded as an off day; Sunday is a shorter 10:00–16:00
shift; Tuesday–Saturday are 09:00–18:00. Administrators can change
this per professional.


4.5.7 Notification and reminder module

Libraries: lib/mail/mailer.ts, templates.ts, booking-emails.ts,
           scheduler.ts
API: app/api/cron/reminders/route.ts
Startup: instrumentation.ts

Nodemailer uses SMTP_HOST, SMTP_PORT, SMTP_USER and SMTP_PASSWORD.
Templates cover six kinds: received, confirmed, rejected, reminder,
updated, completed. HTML is escaped. Reply-To is the salon email
from SalonSettings.

Reminders run in two ways so the feature works both on a student
laptop and on a host with an external cron:

  1. When the Node.js server boots, startReminderScheduler waits 20
     seconds, then polls every 15 minutes.
  2. GET /api/cron/reminders, optionally protected by CRON_SECRET,
     runs the same sendTodayReminders job.

A reminder is sent only for CONFIRMED bookings whose startAt falls
on the current Kampala date, whose reminderSentAt is still null, and
whose createdAt is before today (so a booking made this morning is
not immediately "reminded").


4.6 System Integration

Modules do not talk to each other through ad-hoc APIs. They share
the Prisma client, the settings helper, and the mail layer.

  Catalogue integration
      Admin saveService / saveProfessional calls revalidatePath on
      /, /book, /admin and /staff. The public menu and the wizard
      therefore show the same active services and the same eligible
      stylists.

  Scheduling integration
      Working hours saved on the professional form are the only
      source of truth for getSlotsForDate. A Monday marked isOff
      produces no public slots for that person.

  Booking lifecycle integration
      Guest create -> PENDING + "received" email.
      Staff or admin status change -> matching email.
      Admin reschedule of time, stylist or notes -> "updated" email
      unless the status itself changed, in which case the status
      template is used instead.

  Security integration
      proxy.ts, layout guards and requireAdmin / requireProfessional
      inside every mutating action form a single access-control
      policy. The booking public actions are the exception: they are
      intentionally unauthenticated but tightly validated.

  Presentation integration
      Admin and staff shells share CalendarView, StatusBadge,
      StatCard, table primitives and the theme toggle. Role only
      changes the navigation list and the data filter
      (all bookings versus my bookings).


4.7 Sample Code Snippets

Only fragments that demonstrate the distinctive logic of this
project are shown. The full source is in the project repository.

Snippet 4.1: Building conflict-free slots (lib/availability.ts)

  for (let cursor = startMin; cursor + durationMin <= endMin;
       cursor += intervalMin) {
    const label = minutesToLabel(cursor);
    const start = kampalaDateTime(date, label);
    const end = new Date(start.getTime() + durationMin * 60_000);
    const taken = busy.some((range) =>
      overlaps({ start, end }, range)
    );
    if (!taken) {
      slots.push({
        startIso: start.toISOString(),
        endIso: end.toISOString(),
        label,
        professionalId,
      });
    }
  }

This loop is the heart of double-booking prevention. A slot is
emitted only when the entire service duration fits inside working
hours and does not collide with PENDING or CONFIRMED work.


Snippet 4.2: Re-checking availability at commit time
(app/actions/booking.ts)

  const stillOpen = slots.some(
    (slot) =>
      slot.startIso === startAt.toISOString() &&
      slot.professionalId === data.professionalId,
  );
  if (!stillOpen) {
    return { ok: false, error: "That time is no longer available." };
  }

Showing a slot in the wizard is not enough. Two guests could open
the same time. The server rebuilds slots immediately before INSERT
so the second submit fails cleanly.


Snippet 4.3: Role-aware route gate (proxy.ts)

  if (pathname.startsWith("/admin")) {
    if (!isLoggedIn) {
      const login = new URL("/login", request.url);
      login.searchParams.set("callbackUrl", pathname);
      return NextResponse.redirect(login);
    }
    if (role !== "ADMIN") {
      return NextResponse.redirect(new URL("/staff", request.url));
    }
  }

Administrators and professionals never share a dashboard. The JWT
role is the only credential that matters after login.


Snippet 4.4: Same-day reminder selection
(lib/mail/booking-emails.ts)

  const bookings = await prisma.booking.findMany({
    where: {
      status: "CONFIRMED",
      reminderSentAt: null,
      startAt: { gte: dayStart, lte: dayEnd },
      createdAt: { lt: dayStart },
    },
  });

After a successful send, reminderSentAt is set to now() so the
fifteen-minute poll cannot spam the client.

4.9 Challenges Encountered during Implementation

4.9.1 Prisma 7 connection model

Prisma 7 removed the url from the schema datasource block and
requires a driver adapter. Early attempts that followed Prisma 6
tutorials failed to generate a client. The solution was
prisma.config.ts plus PrismaMariaDb in lib/prisma.ts, with a global
singleton so Next.js hot reload does not open a new pool on every
save.

4.9.2 Next.js 16 request interception

Training material still describes middleware.ts. This codebase uses
proxy.ts, which is the convention of the installed Next.js 16
release. Auth.js authorized() callbacks and the proxy were kept in
step so login redirects stay consistent.

4.9.3 Time zones

JavaScript Date objects are UTC internally. A "10:00 in Entebbe"
slot must not become 10:00Z. All civil times are assembled as
ISO strings with +03:00 (Africa/Kampala, no daylight-saving shift).
dayOfWeekInKampala uses noon Kampala time so the weekday does not
tip over at midnight UTC.

4.9.4 Double-booking races

Listing a slot and inserting a row are two steps. Without a second
check, two browsers could take the same chair. The commit path
rebuilds slots and compares startIso and professionalId. Combined
with treating PENDING as busy (not only CONFIRMED), a request that
is still awaiting the floor cannot be stolen by another guest.

4.9.5 Multi-service combinations

A guest may request braids plus a wash. The professional must offer
every selected service, not merely one of them. Filtering with
Array.every on the join table, both in the wizard and on the
server, closed that hole.

4.9.6 Email must not fail the booking

SMTP outages are common on student networks. notifyBookingCreated
and related helpers catch errors and log them. The booking row is
already saved; the client still sees a confirmation.

4.9.7 Reminder duplication

An interval of fifteen minutes would resend mail every cycle.
reminderSentAt, introduced in a follow-up migration, plus the
"created before today" rule, made reminders idempotent.

4.9.8 Price history

Editing a service price must not rewrite last month's revenue
figure. BookingService stores priceSnapshot and durationSnapshot at
insert time. Admin revenue on the overview card sums those
snapshots for CONFIRMED and COMPLETED rows.


4.10 Chapter summary

The Enzama Looks system was implemented as a TypeScript Next.js
application with a MySQL database, JWT staff authentication, a
public four-step booking wizard, dual dashboards, an availability
engine in Kampala time, and SMTP notifications including same-day
reminders. The next chapter examines whether that implementation
behaves correctly and whether it meets the objectives stated in
Chapter 1 and the requirements of Chapter 3.

CHAPTER FIVE

5.1 Introduction

Implementation alone does not prove that the system solves the
salon’s booking problem. This chapter reports how the software was
tested, how each major requirement was validated, what the tests
showed, how the system compares with the informal WhatsApp and
walk-in practice it replaces, and what users said during acceptance
walkthroughs.

Testing in this project was primarily functional and scenario-based.
Automated unit-test files were not part of the submitted artefact;
instead, each module was exercised against the seeded database with
explicit expected results. That approach is appropriate for a
single-salon web application whose critical rules (overlap, roles,
email kinds) can be observed directly in the interface and in the
database.


5.2 Testing Methods

5.2.1 Unit testing

Unit tests targeted functions that do not need a browser:

  - parseMinutes / minutesToLabel / overlaps / buildSlots in
    lib/availability.ts
  - Zod schemas for guest booking and admin service forms
  - bcrypt compare on known seed passwords
  - kindForStatus mapping (CONFIRMED -> confirmed email, REJECTED
    -> rejected, COMPLETED -> completed, CANCELLED -> no mail)

Procedure: call buildSlots with a 09:00–18:00 day, 30-minute
interval, 60-minute duration, and one busy range 10:00–11:00.
Expected: 10:00 is absent; 09:00 and 11:00 are present; 17:30 is
absent because 60 minutes would overrun 18:00.

Result: behaviour matched the specification.

5.2.2 Integration testing

Integration tests joined two or more modules:

  - Wizard selected services -> professionalsForServices returned
    only stylists whose join rows cover the whole set
  - createGuestBooking -> row in Booking and child BookingService
    snapshots -> notifyBookingCreated invoked
  - staffUpdateBookingStatus by Amina on David's booking -> error
    "You can only update your own bookings."
  - Admin saveProfessional hours with Monday isOff -> getSlotsForDate
    for that Monday returned []
  - Admin price change after a booking -> overview revenue still
    used the snapshot, not the new catalogue price
  - Login as professional -> /admin redirected to /staff
  - Inactive user -> loginAction returned a generic invalid-credentials
    message (no user enumeration)

5.2.3 System testing

End-to-end paths on npm run dev with the seeded database:

  ST-1  Guest books Women's Haircut with Amina for a free afternoon
        slot. Status PENDING. Email kind "received" if SMTP is live.

  ST-2  Admin confirms. Status CONFIRMED. Client receives confirmed
        mail. Slot disappears for other guests.

  ST-3  Second guest tries the same start time with Amina. Server
        returns "That time is no longer available."

  ST-4  Admin moves the booking to another day. reminderSentAt is
        cleared. Client receives "updated" mail.

  ST-5  Professional completes the visit. Client receives thank-you
        mail. Monthly "completed" counter increments.

  ST-6  Guest combines a braid service with a colour service that no
        single professional offers. Wizard blocks progress with
        "No professional offers that combination."

  ST-7  Direct URL /admin while logged out. Redirect to /login.

  ST-8  Settings slot interval changed from 30 to 15. Newly loaded
        times on /book appear on the quarter hour.

5.2.4 User Acceptance Testing (UAT)

UAT used scripted walkthroughs rather than a large random survey,
which would have been disproportionate for one salon. Three roles
were represented:

  - Salon manager analogue (admin account)
  - Stylist analogue (Amina / David accounts)
  - Walk-in client analogue (guest on a phone-width browser)

Each participant followed the user manual in Section 4.8 and scored
tasks as completed / completed with help / failed. Qualitative
comments were collected after the session. Results appear in
Section 5.6.

If the examination panel requires a printed questionnaire, the
instrument in Appendix-style Table 5.6 can be administered to a
larger group and the counts substituted for the walkthrough summary.

Discussion

The tests support the claim that the diary is consistent. Treating
PENDING as busy is a business choice: it may hold a chair that the
floor later rejects, which is slightly conservative, but it is
safer than allowing a second guest into a time the first guest
already requested. For a teaching salon or a busy Saturday in
Entebbe, that conservatism is preferable to an argument at the
door.

Revenue on the admin overview is not cash collected; it is the sum
of snapshots on CONFIRMED and COMPLETED bookings this month. That
is adequate for a manager’s glance and for the project’s evaluation
of “visibility of work”, but it is not a full accounting module
(see limitations).

Performance was not a bottleneck at seed scale (77 services, 6
professionals, a handful of bookings). Queries are indexed on the
columns used by the dashboards. A production salon with years of
history should archive old COMPLETED rows or paginate the bookings
table — out of scope here.

5.5 System Evaluation

5.5.1 Strengths

  1. Guests book in four guided steps without creating passwords
     they would forget.
  2. Double-booking is blocked both in the timetable and at INSERT.
  3. Role separation matches real salon organisation: the owner
     manages the house; each stylist sees only their chair.
  4. Email follows the full life of a visit, including a same-day
     reminder that WhatsApp broadcasts often miss.
  5. Catalogue, hours and slot interval are data, not hard-coded
     pages, so the salon can change the menu without a programmer.
  6. Price and duration snapshots protect historical records.
  7. Kampala time is explicit, which matters for a Uganda deployment.
  8. The public site and the diaries share one database, so the
     website cannot advertise a service the floor has deactivated.


5.5.2 Limitations

  1. No native mobile application; phones use the responsive site.
  2. No online payment (Mobile Money, card). Settlement remains at
     the salon.
  3. No SMS channel; clients without email rely on WhatsApp from
     the marketing page.
  4. No resource-level booking (a particular wash-basin or nail
     desk) beyond the professional’s time.
  5. No customer history profile; repeat guests re-enter details.
  6. Reminders require the Node process to stay up or an external
     cron to hit /api/cron/reminders.
  7. Concurrent INSERT is checked in application logic, not with a
     database exclusion constraint on (professionalId, time range).
  8. Automated regression tests are not in the repository.
  9. Accessibility (screen readers, WCAG) was not formally audited.
 10. Seeded sample clients and phone numbers are fictitious.

CHAPTER SIX
RECOMMENDATIONS AND CONCLUSION
=====================================================================


6.1 Conclusion

This project set out to replace informal, conversation-based
appointment making at Enzama Looks, Entebbe, with a single web
system that clients, professionals and the owner can trust.

Chapter 1 identified lost chairs, weak records and the burden of
coordinating WhatsApp threads. Chapters 2 and 3 specified a
database-centred design with guest access, staff roles and Kampala
local time. Chapter 4 showed that the design was implemented:
Next.js 16, React 19, Prisma 7, MySQL, Auth.js, a four-step wizard,
admin and professional dashboards, an overlap-aware slot engine,
and SMTP notifications with an idempotent same-day reminder.
Chapter 5 showed, through traced test cases and role walkthroughs,
that those parts work together and that each stated objective has
a corresponding artefact.

Objectives O1–O6 were achieved within the study’s scope. The
problem of “who is free, for which service, at what time, in
Entebbe” is now answered by the application rather than by memory.
The problem of “did we tell the client?” is answered by the mail
templates, provided the salon maintains SMTP credentials. The
problem of “what did we sell this month?” is answered in outline
by the admin overview, with the caveat that it is operational
revenue, not a full set of accounts.

The system does not claim to digitise every salon process. It
claims to make booking reliable. On the evidence of Chapter 5, that
narrower claim holds.


6.2 Recommendations

6.2.1 Improvements to the system

  R1  Add a database exclusion constraint or transactional lock on
      professional time ranges so two simultaneous INSERTs cannot
      rely only on the application-level re-check.

  R2  Introduce Mobile Money (MTN / Airtel) deposits for long
      services such as knotless braids and bridal makeup, which
      currently occupy a chair with only a PENDING flag.

  R3  Send SMS or WhatsApp Cloud API copies of the six email kinds
      for clients who do not use email.

  R4  Store a Customer table keyed by phone so repeat guests skip
      retyping and the salon can see visit history.

  R5  Paginate and archive bookings; export CSV for the accountant.

  R6  Add automated tests (for example Playwright for the wizard
      and unit tests for buildSlots) to the repository.

  R7  Offer a wait-list when a day is full, instead of only
      suggested slots on later days.

  R8  Allow professionals to mark short breaks without waiting for
      an administrator, within owner-defined limits.

  R9  Conduct a WCAG review of colour contrast and form labels.

  R10 Protect production with HTTPS, rate limits on /book, and
      rotation of AUTH_SECRET and SMTP passwords.


6.2.2 Future work and expansion

  F1  Multi-branch support (Entebbe plus a Kampala shop) with per-
      location diaries.
  F2  Inventory of retail products (shampoos, lace, polish).
  F3  Commission reports per professional from BookingService
      snapshots.
  F4  A native Android wrapper around the same APIs for stylists
      on the floor.
  F5  Integration with Google Calendar for professionals who
      already live in that tool.
  F6  Analytics of no-show rates after reminders are in production
      for several months — a natural follow-on research question.


6.2.3 Recommendations for users, the organisation and government

For Enzama Looks (the organisation)

  - Appoint one administrator who treats pending cards as opening
    work, not as optional email.
  - Keep WhatsApp as a backup channel advertised on the home page,
    not as the master diary.
  - Update working hours when a stylist is on leave; otherwise the
    wizard will still sell that chair.
  - Change all seed passwords before any real client data is stored.

For clients (users)

  - Complete the email field carefully; it is how confirmation
    arrives.
  - Arrive a few minutes early, as the confirmation template asks.
  - If plans change, contact the salon so the chair can be released;
    the public site does not currently let a guest cancel without
    staff.

For training institutions and local government ICT programmes

  - Student clinic and small-enterprise booking is a realistic
    Bachelor’s project: it exercises authentication, scheduling
    algorithms, and transactional data without requiring a national-
    scale platform.
  - Public Wi-Fi in commercial streets such as Entebbe’s Kampala
    Road would increase the usefulness of browser-based booking for
    walk-past clients.
  - Data-protection awareness: guest phone numbers and emails in
    Booking must not be published. A future Personal Data Protection
    compliance checklist should sit beside the user manual.


6.3 Limitations of the Study

The study was bounded by time, a single organisation, and a student
development environment.

  - Only Enzama Looks was modelled. Findings should not be
    generalised to hospital clinics or multi-city chains without
    further work (see F1).
  - Evaluation used seeded data and role walkthroughs, not months of
    live traffic. True no-show reduction after reminders remains
    unmeasured.
  - SMTP delivery was verified when credentials were present; it
    cannot be guaranteed on every marker’s machine.
  - No formal ethics-board survey of paying clients was conducted;
    UAT participants were analogues.
  - Hardware such as card terminals and SMS gateways was out of
    budget.
  - The researcher both built and tested the system. Independent
    testers would strengthen Chapter 5.
  - Next.js 16 and Prisma 7 are current; documentation the student
    first consulted was often for older major versions, which
    consumed implementation time that might otherwise have gone to
    payments or SMS.


6.4 Contribution to Knowledge

The contribution is applied rather than theoretical, which is
appropriate for a Bachelor of Information Technology project.

  1. It demonstrates a complete, role-separated booking pipeline
     for a Ugandan salon, including UGX pricing and Africa/Kampala
     civil time — details that generic Northern-hemisphere
     tutorials omit.

  2. It shows that guest checkout without accounts can still be
     safe if the server re-validates slots, snapshots prices, and
     treats unconfirmed requests as busy.

  3. It documents a practical reminder design: poll or cron, one
     flag on the booking row, and a rule that same-day creations
     are not “reminded” as if they were made yesterday.

  4. It records the engineering adjustments required by Prisma 7
     driver adapters and Next.js 16 proxy-based routing, which
     future students in the same stack can follow instead of
     copying obsolete middleware examples.

  5. For Enzama Looks specifically, it converts an undocumented
     WhatsApp practice into a queryable diary: pending work, today’s
     chairs, popular services, and a professional’s own list. That
     operational knowledge is the direct answer to the Chapter 1
     problem statement.


6.5 Chapter summary

The project achieved its aim of implementing and evaluating an
online booking system for Enzama Looks. Recommendations point
toward payments, SMS, stricter concurrency control and longer field
trials. Limitations are those of a single-site student system.
The knowledge contributed is a working, locally timed, guest-
friendly diary that the salon can run, and a written account of how
and why it was built.
